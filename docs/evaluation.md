# think3 的比较证据

本页记录已保存的结果、结果能够支持的判断，以及仍待回答的安装价值问题。README 中的数字来自历史评测文件，本次整理没有新增模型执行。

## 数据从哪里来

两次评审均记录于 2026-11-01，是开发过程中的合成行为检查。情境与判据在开发期间编写，独立代理分别阅读一个版本，给出选用判断和拟采取的动作；经验复用回答再由维护评审按判据评分。它们没有招募真实使用者，也没有实际执行情境中的修复、查询、打包或设备操作。

来源链为：**合成情境与判据 → 各版本的代理文本输出 → 选用计数或语义评分 → 本页汇总**。输出里“下一步会做什么”记录的是建议，不能算作完成该动作的证据。现有比较覆盖 1.2.2 与 1.3.0 的选用判断，以及 1.3.0 与 1.3.1 的经验复用建议。

## 现有结果

| 项目 | 基线 | 候选 | 计数依据 |
| --- | --- | --- | --- |
| 选用判断与预设标签一致 | 1.2.2：14/16 | 1.3.0：16/16 | 按 16 个案例 ID 比较 `select` 与判据 |
| 7 个不应介入的情境中误选 | 1.2.2：0/7 | 1.3.0：0/7 | 预设标签为 false，却选择 Skill 的次数 |
| 经验复用建议通过原语义评审 | 1.3.0：8/8 | 1.3.1：8/8 | 保留原维护评审的逐例 pass 与说明 |

选用数据已在整理时从逐例输出重新计算。经验复用的“通过”是原评审者的语义判断；公开原输出与判据，便于读者复核，不能将它当成已经完成任务的自动验收。

### 选用变化与反证

两版的选择仅在 S08、S09 不同：

- **S08：** 未确认接口尺寸，就准备批量生成 20 个变体。1.3.0 选择调用 Skill；1.2.2 没有选择，但同样提出先查规格表、核对尺寸。
- **S09：** 只验证预览能打开，就准备声称文件可直接发送到设备。1.3.0 选择调用 Skill；1.2.2 没有选择，但同样提出对照成功旧包检查发送元数据，并限定交付结论。

因此，14/16 → 16/16 支持的是“本组场景中，选用判断更符合预设标签”。它不支持“多解决两个问题”，也不能写成任务成功率、生产环境触发率或返工改善比例。

### 经验复用的平局

两版在 8 个情境中都通过原评审。两者都能提出按条件复用旧证据、遵循撤回与替代关系、修正实际使用的执行入口。

R01 中，候选版把追加设备导入检查与输出差异联系起来；基线版直接提出导入检查。这是行动安排的差异，但没有实际执行或成本记录，无法据此计算节省的时间。

**注意 R08 的来源：** 测试输入自身包含“旧新版均 8/8”的假设，是让代理判断能否据此宣称省时的题目。上表的真实历史计数来自另存的两组模型输出和原评审结果，而非把 R08 的题目内容当成实验成绩。

## 能复现到哪一步

| 层次 | 现在可以怎样做 | 能确认的范围 |
| --- | --- | --- |
| 核验文件 | 对照汇总中的 `exported_file_sha256` 与 `input_sha256` 计算 SHA-256；仓库文件使用 UTF-8、LF 换行 | 文件与保存的校验值一致；哈希本身不证明实验合理或产品有效 |
| 重算计数 | 运行下方代码，逐例比较 `select` 与预设标签 | 得到 14/16、16/16 与双方 0/7 |
| 重评语义 | 读取两版经验复用回答，按公开判据重新评分 | 可检查原评审的 8/8 判断；不同评审者可能有分歧，应保留理由 |
| 严格重跑模型生成 | 当前资料不足 | 缺少可核对的完整模型配置、调用输入和执行轨迹；无法严格重建原实验 |

下方代码只读取已有 JSON 并计数，不调用模型。重新提交这些情境给一个模型，会得到一次新的试验，不能据此声称复现了原始生成过程。

## 文件与计数方法

输入与判据：

- [16 个选用情境](../tests/routing-cases.json) 与 [选用判据](../tests/routing-criteria.json)。
- [8 个经验复用情境](../tests/reuse-cases.json) 与 [经验复用判据](../tests/reuse-criteria.json)。

保存的行为输出与评审：

- [1.2.2 选用输出](../validation/behavior-comparisons/routing-1.2.2.json)、[1.3.0 选用输出](../validation/behavior-comparisons/routing-1.3.0.json)。
- [1.3.0 经验复用输出](../validation/behavior-comparisons/reuse-1.3.0.json)、[1.3.1 经验复用输出](../validation/behavior-comparisons/reuse-1.3.1.json)。
- [原逐例语义评审](../validation/behavior-comparisons/reuse-review.json)、[计数、来源与 SHA-256](../validation/behavior-comparisons/summary.json)。

在仓库根目录用 Python 标准库重算选用结果：

```python
import json
from pathlib import Path

root = Path.cwd()
expected = json.loads((root / "tests/routing-criteria.json").read_text(encoding="utf-8"))["selection"]
for version in ("1.2.2", "1.3.0"):
    path = root / f"validation/behavior-comparisons/routing-{version}.json"
    cases = json.loads(path.read_text(encoding="utf-8"))["cases"]
    matched = sum(row["select"] == expected[row["id"]] for row in cases)
    false_selections = sum(row["select"] and not expected[row["id"]] for row in cases)
    negatives = sum(not value for value in expected.values())
    print(version, f"matches={matched}/{len(cases)}", f"false_selections={false_selections}/{negatives}")
```

预期输出：

```text
1.2.2 matches=14/16 false_selections=0/7
1.3.0 matches=16/16 false_selections=0/7
```

## 保存与解释的边界

- 每版各一次独立代理模拟；同组情境在一次会话批次中处理，不是 16 或 8 次独立重复试验。
- 原记录称先根据描述冻结选用，再阅读正文提出行动，执行者没有看到另一版或评分判据。公开的最终输出无法独立证明完整读取顺序。
- 保存结果没有可核对的模型型号、推理档位、采样配置、耗时或 token 用量，不能称为严格同模型受控实验。
- 情境围绕设计目标编写，没有独立留出集；经验复用由维护评审按判据评分，没有独立双盲评分。
- 没有无 Skill、简短提示或其他 Skill 的执行基线，也没有真实宿主自动选用率、完整任务成功率、返工量或用户纠正次数的数据。
- 1.3.2 的复盘规则沿用 1.3.1；本页保留实际受评版本，不把旧结果改名为 1.3.2 的新测试。

公开副本保留逐例输出文字和原复用评审字段，移除了顶层本机路径与其他非行为材料。输入、判据与原评测文件内容相同；受评入口与对应 Git 标签核对一致。汇总分别记录原文件和公开副本的 SHA-256，导出时间与原评测日期分开保存。私人历史、真实账本、安装记录不随这些材料发布。

## 时间怎样参与判断

评测日期和发布时间用于追溯版本；日期更新或迭代次数更多，本身不能证明能力更强。任务耗时则是需要与质量一起看的成本指标，现有历史评测没有保存可供比较的耗时数据。

对 think3，先看用户的监督负担与实际交付：任务是否通过验收，用户额外纠正几次，是否无依据宣称完成，同类错误是否再次出现，必要改进是否进入实际使用的代码或检查步骤。再看为此增加的检查次数、总耗时、token 与工具调用成本。

少做验证可能缩短时间，多一次必要检查可能避免后续返工；模型服务、网络、工具等待和用户回复也会影响耗时。只有控制模型、任务、工具、质量要求与预算，重复比较并记录这些影响，才有依据讨论时间差与 Skill 的关系。即使某组更快，也要同时报告验收结果、失败和超预算执行。

## 下一轮要检验的安装价值

**以下是待执行方案，没有实验成绩。** 最关键的比较是同一代理在三个条件下，是否以合理成本完成相同任务：

| 条件 | 提供给代理的额外材料 |
| --- | --- |
| 原生代理 | 无 think3、无额外复盘提示 |
| 简短提示 | 固定提示：“继续前核对目标、证据和下一步；发现偏差就纠正，没问题就继续。检查保持简短，把必要改进落实到实际执行入口。” |
| think3 | 指定版本的完整 Skill，按受测宿主的正常发现与加载方式使用 |

先冻结模型版本、推理设置、工具、任务输入、验收标准与执行预算。使用独立会话，防止上一组结果、评分答案或已安装的其他版本泄漏到基线；平衡执行顺序并重复运行。现有场景作为开发材料，另准备未用于修改 Skill 的留出任务，覆盖需要纠偏和正常工作两类。

按上面的交付、监督负担和成本指标评分。另设后续关联任务，检查已纠正的错误是否复发、落实到执行入口的改进是否真的生效；当前没有这类连续任务数据。复盘说得好听不单独加分。

自动选用需要另看宿主记录中的发现、读取和介入过程。强制加载后的能力测试不能拿来宣称自动触发效果；负例中的额外操作和成本同样计入结果。

逐案例公开三组输出、产物、评分理由和配置。若 think3 与简短提示打平而成本更高，就应缩小推荐范围或精简规则；只有完成对照，才讨论可以支持什么程度的优势主张。
